# Cockpit

Cockpit은 프로젝트의 `PROGRESS.md` 파일을 읽어 브라우저에서 실시간으로 시각화해 주는 초경량 로컬 프로젝트 대시보드(Map-first Thin PM Cockpit)입니다.

프로젝트 상태를 일반 마크다운(Markdown)으로 작성해 두면, Cockpit이 이를 파싱하여 구조화된 프로젝트 지도, 현재 상황 및 다음 전환, 영역별 상세 검사기(Inspector)를 제공합니다.

---

## 1. 사용 전 준비사항

- **Node.js**: Vite 7 툴체인 호환 버전 (`^20.19.0` 또는 `>=22.12.0`, npm 포함)
- **Git**: npm의 GitHub 패키지 설치 시 필요

---

## 2. 설치 및 업데이트 방법

GitHub 저장소(`main` 브랜치)에서 직접 전역 설치합니다:

```bash
npm install -g --install-links "github:savior714/cockpit#main"
```

*(최신 버전으로 업데이트할 때도 동일한 명령어를 다시 실행하면 됩니다.)*

---

## 3. 프로젝트 구성 및 실행

### 권장 프로젝트 구조

프로젝트 최상위 루트에 `PROGRESS.md` 파일을 배치하는 것을 권장합니다:

```text
my-project/
├── ...
└── PROGRESS.md
```

### 실행하기

프로젝트 루트 디렉터리에서 `cockpit` 명령어만 입력하면 됩니다:

```bash
cd my-project
cockpit
```

- 기본 브라우저가 자동으로 열리며 대시보드(`http://127.0.0.1:4321`)가 표시됩니다.
- Cockpit은 `127.0.0.1` 루프백 전용으로 바인딩되며 읽기 전용(Read-only)으로 안전하게 동작합니다.

### 다른 경로의 파일 지정하기

다른 위치에 있는 파일이나 다른 이름의 마크다운 파일을 지정할 수도 있습니다:

```bash
cockpit /path/to/another/PROGRESS.md
cockpit ./docs/PROGRESS.md --port 5000 --no-open
```

#### CLI 옵션

- `cockpit [path/to/PROGRESS.md]` — 대상 파일 경로 (생략 시 현재 디렉터리의 `./PROGRESS.md`)
- `--port`, `-p` — 포트 번호 지정 (기본값: `4321`)
- `--no-open` — 브라우저 자동 실행 비활성화
- `--help`, `-h` — 도움말 출력

## 4. Cockpit 동작 원리 및 워크플로우

### 권위 경계 및 동작 원리

Cockpit의 역할과 데이터 흐름은 다음과 같이 명확히 분리되어 있습니다:

```text
repo / runtime / 관련 SSOT (최신 실제 증거)
        ↓ (대조 및 갱신)
외부 역량 에이전트 (Claude Code, ChatGPT, Gemini 등)
        ↓ (작성/저장)
   PROGRESS.md (Cockpit이 읽는 단일 현황 문서)
        ↓ (시각화)
     Cockpit
```

- **단일 문서 시각화**: Cockpit은 지정된 단일 `PROGRESS.md` 문서만을 읽어 화면에 표시하며, 저장소나 런타임을 직접 검사·분석하지 않습니다.
- **실제 증거 우선**: `PROGRESS.md`는 Cockpit이 읽고 보여주는 단일 현황 문서일 뿐, 최신 코드/런타임/도메인 증거보다 상위의 권위를 갖지 않습니다. 프로젝트 실재가 바뀌면 `PROGRESS.md`는 진부화(stale)될 수 있으며, 실제 증거와 충돌 시 언제나 최신 실제 증거가 우선합니다.
- **외부 에이전트 갱신**: 프로젝트 상태가 달라지면 외부 코딩 에이전트가 최신 실제 증거와 기존 문서를 대조하여 `PROGRESS.md`를 갱신합니다.
- **자동 새로고침 (Live Reload)**: Cockpit은 대상 `PROGRESS.md` 파일 저장을 감시하여 브라우저 새로고침 없이 화면을 즉시 갱신합니다.

### 처음 시작할 때: 새 프로젝트에 PROGRESS.md 작성 요청하기 (First-Use Prompt)

새로운 프로젝트나 기존 프로젝트에 처음 Cockpit을 연결할 때는 외부 역량 에이전트(Claude Code, ChatGPT, Gemini 등)에게 다음 프롬프트를 그대로 복사하여 전달합니다:

```text
이 프로젝트의 실제 상태를 파악하여 Cockpit용 `PROGRESS.md` 문서를 작성해줘.

[6단계 증거 우선 동화 및 독자 중심 종합 절차 (Evidence-First Assimilation & Reader-Facing Synthesis Pass)]
1. 이해 (UNDERSTAND): 프로젝트의 실제 목적, 주요 사용자/소비자, 시스템/제품 경계, 저장소 로컬 권위 문서를 파악한다.
2. 분해 (DECOMPOSE): 새로운 사람이 보아도 프로젝트의 전체 멘탈 모델을 온전히 복원할 수 있는 프로젝트 고유의 실질적 핵심 영역(Material Areas)과 독립적인 지도 축(H3 레일)을 도출한다.
   - 독립 축 테스트 (Independent Map Axis Test):
     "새로운 독자가 단 하나의 지도 축만으로 프로젝트의 중요한 멘탈 모델을 온전히 복원할 수 있는가, 아니면 서로 다른 독립적인 관계 유형들이 별개의 축(H3 레일)으로 분리되어야 하는가?"
     * 독립적 관계 유형의 예시:
       - 제품/사용자 작업의 흐름 (How product/user work flows)
       - 시스템 구성요소 상호작용 및 아키텍처 (How system components interact)
       - 데이터 이동 및 파이프라인 (How data moves)
       - 운영/서비스 조직화 및 처리 방식 (How operations are organized)
       - 연구/분석 절차 (How research/analysis proceeds)
       - 실제 도입/준비도/성숙도 여정 (How rollout/readiness/adoption progresses)
     * (위 항목들은 예시일 뿐 고정 분류 체계가 아니며, 실제 저장소 증거로부터 프로젝트에 맞는 축과 의미를 직접 도출해야 함)
     * 서로 다른 질문에 답하는 영역 집합들은 하나의 혼합된 맵으로 압축하지 않고 독립된 H3 레일로 분리한다.
3. 검증 (VERIFY): 각 영역마다 실제 구현 코드, 테스트/검증 결과, 런타임/외부 증거를 직접 대조·확인한다. (기존 README, 로드맵, TODO 등은 시작점일 뿐 구현 주장의 독립적 증거가 아님)
4. 종합 (SYNTHESIZE): 검증된 구현 증거를 단순 번역하지 않고, 이 저장소를 모르는 독자를 위해 "이 영역이 무엇인지, 이 프로젝트에서 왜 중요한지, 현재 실제로 무엇이 확립되었는지, 실질적으로 무엇이 미완성/불확실한지"를 중심으로 의미를 먼저 구성한다.
5. 작성 (WRITE): 아래 마크다운 구조와 원칙에 맞춰 사실 기반으로 작성하되, 기술 증거는 점진적 공개(근거 섹션 또는 부차적 설명)로 배치한다.
6. 자가 감사 및 독자 테스트 (READER TEST & AUDIT): 외부인 관점에서 아래 '독자 테스트(Reader Test)'와 구조 감사를 수행한 후 완료한다.

다음 마크다운 구조와 작성 원칙을 지켜줘:

# [프로젝트 이름]

## 프로젝트 지도

### [프로젝트 고유의 1차 분류 레일]
#### [해당 레일 내부의 논리적 그룹]
- **[영역 이름]** — 해당 영역이 프로젝트에 기여하는 실질적 역할/가치를 담은 한 줄 요약 (단순 엔지니어링 라벨이나 아티팩트 나열 금지)

#### [프로젝트 전체의 현재 집중 전선인 경우: 현재 단계]
- **[영역 이름]** — 지금 프로젝트 전체에서 실제로 집중하고 있는 핵심 단일 영역

### [프로젝트 고유의 2차 분류 레일 (독립적인 멘탈 모델 축이 존재하는 경우에만 추가)]
#### [논리적 그룹]
- **[영역 이름]** — 해당 영역이 프로젝트에 기여하는 실질적 역할/가치를 담은 한 줄 요약

## 영역 상세 (또는 영역별 상세)

### [지도에 등장한 동일한 영역 이름]

#### 의미
해당 영역이 이 시스템/프로젝트에서 수행하는 실질적인 목적, 역할 및 경계 맥락 (저장소를 모르는 독자도 이해할 수 있도록 설명).

#### 현재 수준
인간이 이해할 수 있는 프로젝트 언어로 현재 실제로 확립되었거나 증명된 기능/상태를 먼저 기술하고, 중요한 실질적 한계를 명시한다 (기술적 세부 증거는 근거 섹션에 배치).

#### 남은 문제
- 해당 영역의 실제 완성도나 위험을 파악하는 데 필요한 구체적 미해결 문제와 실질적 파급 효과 (단순 내부 라벨 축소 금지, 0개·1개 또는 여러 항목).

#### 근거
- 현재 수준과 주장을 뒷받침하는 구체적인 코드 파일, 테스트 슈트, 런타임/운영 증거, 커밋 등 기술적 세부 증거 (단순 "코드 확인 완료" 같은 일반론 금지).

### [지도에 등장한 다음 영역 이름...]
(지도에 나열된 모든 검사 대상 영역마다 위 4개 항목을 동일한 영역 제목(H3)으로 빠짐없이 작성할 것)

## 현재 상황
프로젝트 전체 관점에서 지금 실제로 진행 중인 핵심 상황 2~3줄 요약.

## 다음 전환
현재 단계가 완료된 후 일어날 구체적인 다음 1단계 전환.

## 직면한 문제
- 현재 진행을 가로막고 있거나 집중적인 해결이 필요한 실질적 장애 요인.

[작성 및 진입 원칙]
1. 지도 항목 진입 기준 및 독립 축 분해 (Map Item Admission & Independent Map Axes):
   - 지도 항목은 프로젝트/제품/시스템의 실질적 관심사를 대표해야 한다.
   - 지도 탈락 기준: "이 항목이 지도에서 사라졌을 때, 새로운 독자가 프로젝트가 무엇을 하는지, 핵심 시스템/제품이 어떻게 구성되는지, 또는 프로젝트가 현재 어디에 서 있는지를 이해하는 데 실질적 손실이 발생하는가?" — NO라면 지도 항목으로 승격하지 않는다.
   - 기본 제외 대상 (NON-MAP): 단순 저장소 메카닉(현재 브랜치, HEAD 기준선, clean working tree, 저장소 관리 상태, 문서 최신성, 테스트 명령어 목록 등 일반적인 개발 메카닉)은 지도가 아닌 맥락/근거에 기록한다 (해당 메카닉 자체가 프로젝트의 릴리스 전선인 예외적 경우 제외).
   - "제품 기능 기반", "운영 안전 경계" 같은 막연한 단일 우산(umbrella) 항목으로 뭉개지 말고, 구현/검증 증거와 미해결 과제가 서로 다른 실질적 관심사 단위로 명확히 분리한다.

2. 축 충분성 테스트 및 관계 유형 분리 (Axis Sufficiency Test & Separation of Relation Types):
   - 각 제안된 레일마다 해당 레일이 답하는 평이한 언어의 질문을 정의한다 (예: "사용자/고객의 작업이 이 시스템에서 어떻게 흘러가는가?", "어떤 주요 구성요소들이 결합되어 시스템을 작동시키는가?", "실제 운영/도입에 이르기까지 이 프로젝트는 지금 어디쯤 와 있는가?" 등. 정확한 질문은 프로젝트 증거에서 직접 도출).
   - 레일 sufficiency 자문: "이 레일을 완전히 제거했을 때, 새로운 독자가 프로젝트의 멘탈 모델 중 어떤 중요한 부분을 잃어버리게 되는가?"
     * 고유하고 뚜렷한 손실이 없다면 그 레일은 중복/불필요할 가능성이 높다.
     * 새로운 독자의 중대한 핵심 질문에 답하는 레일이 전혀 없다면 분해가 불완전한 것이다.
     * 기계적으로 레일 수를 늘리지 말고, 프로젝트의 멘탈 모델을 온전히 복원하는 가장 간결하고 독립적인 레일 집합을 유지한다. (단일 축으로 충분한 프로젝트는 1개 레일만 유지)
   - 서로 다른 관계 유형의 혼합 금지: 단지 모두 '중요하다'는 이유만으로 성격이 다른 항목들을 하나의 레일에 뭉개 넣지 않는다. 하나의 레일 내부 그룹/항목들은 일관된 관계를 가져야 한다 (예: 서비스가 실제로 동작하는 업무 흐름과 프로젝트가 시간에 따라 성숙해가는 도입 여정은 서로 다른 축이므로 하나의 레일로 병합하지 않음).

3. 현재 단계(Current Stage) 단일 소유권 (Single Current Stage Ownership):
   - 프로젝트 전체의 핵심 단일 전선인 경우 해당 그룹 헤딩을 정확히 `#### 현재 단계` (영문: `#### Current Stage`)로 지정한다.
   - 프로젝트 전체의 현재 집중 전선은 오직 하나만 존재한다. 해당 전선을 실질적으로 포함하는 단 하나의 레일만 `#### 현재 단계` 그룹을 소유하며, 다른 레일들은 일반 중립 레일로 유지한다 (모든 레일에 억지로 '현재' 그룹을 붙이지 않음).

4. 정보 계층 분리와 의미 우선 언어 (Information Hierarchy & Meaning-First):
   - 1차 독서면 (First-Reading / Human-Facing): 지도 제목, 지도 한 줄 요약, '의미', '현재 수준' 도입부, '남은 문제'.
   - 2차 기술 증거 (Secondary Technical Evidence): 코드 경로, 테스트 슈트명, 커밋 SHA, Git 브랜치/HEAD 상세, 인프라 내부 구현, 설정/API 식별자 등.
   - 내부 엔지니어링 은어나 약어를 앞세우지 말고, 실질적인 프로젝트 관심사를 먼저 설명한 뒤 세부 증거에 정확한 기술 용어를 배치한다.
     * 지양: "P0 계약 정합성 / 프로바이더 매퍼 / 프로덕션 SHA 정리"
     * 권장: 사용자와 비즈니스 관점의 실질적 문제를 먼저 설명하고 세부 구현 용어는 부차적 증거로 보존
   - 무분별한 한영 혼용(예: "운영 전 readiness" -> 명확한 프로젝트 표현 사용)을 지양하되, 정립된 도메인 전문 용어는 정밀도를 위해 유지하고 첫 등장 시 실질적 의미를 함께 설명한다.

5. 지도 요약 품질 (Map Summary Quality):
   - 각 영역 카드의 한 줄 요약은 저장소 내부 사정을 이미 알고 있어야만 이해할 수 있는 내부 약어나 라벨 나열을 배제하고, 해당 영역이 프로젝트에 기여하는 실질적 가치를 설명한다.

6. 영역 상세 작성 계약 (Area Detail Contract):
   - `#### 의미`: 외부인에게 해당 영역의 실질적 역할과 경계를 설명.
   - `#### 현재 수준`: 인간이 이해 가능한 수준/상태를 먼저 서술하고 한계 명시.
   - `#### 남은 문제`: 미해결 결과와 맥락을 구체적으로 기술.
   - `#### 근거`: 코드 경로, 테스트, 런타임 결과, 커밋 등 가장 구체적인 구현 증거 배치.
   - `#### 다시 열리는 조건`: 향후 특정 변경으로 재작업이 필요한 경우 선택적 추가.

7. 독자 테스트 및 2중 자가 감사 (Reader Test & Self-Audit):
   - 전체 지도 독자 테스트 (Map-Level Reader Test):
     전체 프로젝트 지도를 읽은 뒤, 저장소를 처음 보는 기술적 독자가 다음 두 가지(또는 프로젝트 고유의 핵심 질문)에 답할 수 있는지 자문한다:
     (1) WHAT (무엇인가 & 어떻게 구성되는가): 이 프로젝트/시스템이 실제로 무엇을 하며, 핵심 관심사들이 어떻게 조직되어 있는가?
     (2) WHERE (어디에 있는가): 이 프로젝트가 현재 어느 지점에 서 있는가? (시간적/준비도/도입 경로 차원이 실질적으로 중요한 프로젝트의 경우. 프로젝트에 준비도 여정이 불필요한 경우 억지로 WHERE 레일을 만들지 않음)
   - 개별 영역 독자 테스트 (Area-Level Reader Test):
     모든 지도 영역에 대해 [지도 제목, 한 줄 요약, 의미, 현재 수준, 남은 문제]만 읽고, 저장소를 읽지 않은 기술적 소양을 가진 독자가 다음 4가지에 답할 수 있는지 자문한다:
     (1) 이것이 무엇인가?
     (2) 프로젝트에서 왜 중요한가?
     (3) 현재 실제로 작동/증명된 것은 무엇인가?
     (4) 실질적으로 미완성이거나 위험한 부분은 무엇인가?
     -> 답변할 수 없다면 일반적인 수식어를 늘리지 말고, 이미 검증된 증거를 바탕으로 설명을 다시 작성한다.
   - 구조 감사: 지도의 모든 항목이 '## 영역 상세'에 동일한 H3 제목으로 1:1 대응되는지 확인한다.
```

### 작업 중 PROGRESS.md 갱신하기

작업을 진행한 뒤 사용자가 직접 외부의 역량 있는 코딩 에이전트(Claude Code, ChatGPT, Gemini 등)에게 다음과 같이 요청하여 `PROGRESS.md`를 갱신합니다:

```text
"이 프로젝트의 기존 PROGRESS.md를 먼저 읽고,
현재 repo/runtime/SSOT의 실제 상태/증거와 대조한 뒤
달라진 부분만 보수적으로 갱신해줘.
독자 관점의 의미(의미, 현재 수준, 남은 문제)를 명확히 유지하고,
미해결된 실질적 문제들을 누락 없이 보존하며,
확인되지 않은 성공을 성급히 주장하지 마."
```

에이전트가 `PROGRESS.md`를 저장하면, 열려 있는 Cockpit 화면에 즉시 변경사항이 반영됩니다.

## 5. PROGRESS.md 핵심 시맨틱

Cockpit v0.3은 프로젝트의 실질적인 진척과 상태를 정확하게 파악할 수 있도록 다음과 같은 시맨틱 구조와 정보 계층을 사용합니다:

### 독자 중심 정보 계층 (Information Hierarchy)

- **1차 독서면 (First-Reading Surface)**: 프로젝트 지도 카드(제목 및 한 줄 요약), 영역 상세의 `의미`, `현재 수준` 도입부, `남은 문제`. 저장소를 처음 보는 사람도 프로젝트 관점에서 무엇이고, 왜 중요하며, 현재 무엇이 가능하고 무엇이 미해결인지 즉시 파악할 수 있는 영역입니다.
- **2차 기술 증거 (Secondary Evidence)**: `근거` 및 세부 구현 경로, 테스트 슈트, 커밋, 런타임 관측치. 1차 독서면의 주장을 뒷받침하는 기술적 세부 정보로 점진적 공개(Progressive Disclosure)됩니다.

### 영역 상세 시맨틱

- **`의미`**: 해당 영역의 실질적인 목적, 역할 및 경계 맥락 (저장소를 모르는 사람도 이해할 수 있는 설명)
- **`현재 수준`**: 현재 실제로 수립되었거나 증명된 구현/기능 수준 (과대평가 방지 한계 포함)
- **`남은 문제`**: 해당 영역의 실제 상태를 이해하는 데 필요한 실질적 미해결 문제들 (여러 항목이 존재할 수 있으며, 단순히 "다음 목표 1개"로 축소하지 않음)
- **`다시 열리는 조건`**: 기존에 안정화되었던 영역을 다시 검토하거나 재작업해야 하는 향후 조건/근거 (선택 사항)
- **`근거`**: 현재 수준 및 상태 주장을 뒷받침하는 실제 코드, 테스트, 런타임, 커밋 증거
- **`다음 전환`**: 프로젝트 차원에서 다음에 일어날 의미 있는 한 단계 전환
- **`이 영역 검토하기`**: 지도에서 영역 카드를 클릭하면 나타나는 우측 검사기(Inspector)의 버튼으로, 외부 추론 에이전트나 모델에 전달할 수 있도록 해당 영역의 맥락과 검토 프롬프트를 원클릭으로 클립보드에 복사합니다.

### 마크다운 섹션 구성

Cockpit은 한국어와 영어 `## h2` 헤딩을 모두 지원합니다:

| 섹션 (한국어) | Section (English) | 패널 설명 |
|---|---|---|
| `## 프로젝트 지도` | `## Project Map` | 프로젝트 고유의 레일/그룹 구조 및 영역 카드 렌더링 |
| `## 영역 상세` / `## 영역별 상세` | `## Area Details` / `## Area Detail` | 각 영역의 세부 속성(의미, 현재 수준, 남은 문제, 근거, 다시 열리는 조건) |
| `## 현재 상황` / `## 지금` / `## 지금 하는 일` | `## Current Situation` / `## Current Frontier` | 우측 기본 개요: 현재 상황 |
| `## 다음 전환` / `## 다음` | `## Next Transition` / `## Next` | 우측 기본 개요: 다음 전환 |
| `## 직면한 문제` / `## 막힌 것` | `## Facing Issues` / `## Blocked` | 우측 기본 개요: 직면한 문제 |
| `## 제품 목표` / `## 프로젝트 큰 그림` | `## Product Goals` / `## Product Goal` / `## Project Frame` | 하단 맥락 카드 |
| `## 확정된 방향` / `## 이미 정해진 방향` | `## Settled Direction` | 하단 맥락 카드 |
| `## 최근 진척` / `## 최근 완료` | `## Recently Completed` / `## Recent Progress` | 하단 맥락 카드 |

*(일반 Mermaid 다이어그램 코드 블록도 지원되며 기존과 동일하게 렌더링됩니다.)*

## 6. 개발자 가이드 (Cockpit 소스 코드 수정 시)

Cockpit 소스 코드를 직접 수정하고 빌드하는 경우:

```bash
# 의존성 설치
npm install

# Vite 개발 서버 실행
npm run dev

# 타입 검사 및 프로덕션 빌드 (dist/ 생성)
npm run build

# 로컬 빌드 파일로 실행 테스트
npm run cockpit -- /path/to/PROGRESS.md

# 배포용 tarball 패키징 (사전 빌드 자동 실행)
npm pack
```

### 디렉터리 구조

```text
cockpit/
├── index.html           # 대시보드 HTML 구조 (지도, 개요, 영역 검사기 슬롯)
├── src/
│   ├── main.ts          # 마크다운 파싱, 네이티브 지도 생성, 검사기 상태 제어, SSE 연동
│   └── style.css        # 지도/검사기 반응형 그리드 및 테마 스타일
├── scripts/
│   └── serve.mjs        # 루프백 HTTP 서버 + SSE 파일 변경 감시 CLI
├── docs/operations/
│   ├── DEVELOPMENT.md   # 개발 실행 원칙
│   └── TESTING.md       # 검증 및 증거 기준
├── package.json
└── tsconfig.json
```
